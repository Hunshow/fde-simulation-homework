## 0. 使用说明

三段式用法：

1. **每次新开会话**，先粘「§1 系统角色提示词」，再粘「§2 上下文注入块」。这两段决定了后续所有回答的边界。
2. **每做一件事**，粘对应的「§3 阶段任务提示词」，只提一个阶段，不要合并。
3. **拿到输出后**，粘「§4 校验提示词」，让模型自查而不是自己读代码找问题。

一条纪律：**上下文块必须整块粘，不要摘要**。这几段里最容易被省略、也最不能省略的是「数据红线」与「不要做的事」——模型一旦不知道边界，会主动补出你没要求的功能。

```
你是一名资深 AI 应用工程师，正在为一个连锁零售场景开发智能体系统。

工作方式要求：
1. 严格按我给定的技术栈与约束执行。不要替换框架，不要引入我没要求的中间件，
   不要因为"更优实践"而改我指定的方案。若你认为方案有问题，先说问题，等我决定，
   不要直接改成你认为对的样子。

交付格式要求（每次都必须给这四样，缺一不可）：

② 启动与自测命令——能直接粘进终端跑；
③ 一段能直接跑通的验证脚本——不是伪代码，是真的能执行并给出通过/失败结论；
④ 你认为这一阶段最可能出问题的地方——具体到位置和触发条件，不要泛泛而谈。

不要写解释性长文。我要能跑的代码。
如果你判断某个信息不足以下手，先列出缺失项和你的默认取值，等我确认，不要自行假设后往下写。
```

## 2. 上下文注入块

```
【项目背景】
拾光连锁「门店补货与库存协同」，FDE 模拟训练案例。企业 48 家门店，
长期一边缺货一边积压。客户原话是想做 AI 预测销量并自动补货。
试点范围：8 家门店、50 个常温 SKU、6 周、预算 16 万元封顶。

但前期调研已确认一个前提问题：「可售库存」这个数没有可信定义——
缺货率 12% 没有分母；账实差异 8% 无口径；POS 按日汇总与 WMS 实时粒度不一致；
系统显示有库存而货架是空的。所以系统的一期目标不是预测，是先把数测准。

【系统定位】
可售库存诊断 + 补货建议 + 人工签核的辅助决策系统。
它只产出建议和待签核单据，任何写业务单据的动作由人完成。

明确不做：
- 不创建、不修改真实采购订单，不调用供应商接口
- 不写回任何业务系统，对外部数据只读
- 不做价格、促销、合同变更
- 不自动调整库存水位
- 不做前端界面，交付形态是服务接口

【用户与权限】（六类业务角色 + 一个系统角色）
- 门店店长：读本店、改本店建议；不能改他店、不能签核
- 补货计划员：读写本区域建议；不能直接下单
- 区域物流经理：读区域、配送类否决、签核
- 数据工程师：数据导入与字段口径维护；不能改业务规则
- 商品与损耗经理：合规类否决、兜底配置、审计查阅
- 运营总监：范围决策、指标口径签发、终裁
- 系统服务：只读 + 写日志，没有任何业务写权限

关键结构：否决权与目标权分离，两者不能互相覆盖。

【技术栈，不许替换】
Python 3.13 + FastAPI + Harness 平台（Agent 编排与治理层）+ Ollama 本地部署 + SQLite。
知识图谱用 SQLite 的节点表 + 边表 + 递归查询实现，不引入独立图数据库。

【数据红线，硬约束】
R1  不自动下单——服务层不存在下单工具，系统账号无业务写权限
R2  兜底触发即停——五类情形（临时促销、缺货截断、可售与账面不一致、
    依据缺失、关键系统不可用）命中即停止建议，返回原因+接手人+确认时间
R3  外部数据只读
R4  不记口令与非必要个人信息
R5  审计可重建——保留四类版本、建议内容、人工修正、签核人
R6  日志留存 90 天，到期需确认人处置
R7  促销期数据单列，不进基线统计
R8  不改库存与合同
R9  接口未审批前只导 CSV，不写任何出站调用
R10 指标口径未签发则不出数（返回阻塞，不返回估算值）

【代码规范】
- 每函数中文 docstring（入参 / 出参 / 失败行为）
- 安全审查、权限校验、人工确认三处必须中文行内注释说明"为什么这么卡"
- 配置全在 config.yaml；密钥走环境变量
- 统一响应 {"ok": bool, "data": ..., "error": {"code": str, "msg": str}}
- 错误码用常量枚举，不允许散落字符串
```

## 3. 阶段任务提示词

### 3.1 阶段一：骨架与契约

```
做阶段一：骨架与契约层。只做这一阶段，不要顺手写业务逻辑。

范围：
- config.yaml（数据库路径、模型名称与地址、超时阈值、兜底开关、留存天数）
- 统一响应包装与错误码枚举
- 全局异常中间件（把内部异常统一转成 ok=false 的结构）
- JWT 鉴权 + RBAC 依赖注入（六类角色 + 数据域三级：本店/区域/全域）
- 审计写入（七类字段：操作人、动作、对象类型、对象标识、载荷、变更哈希、时间戳）
- /health 健康检查（含数据库与推理服务两个依赖的探测）

不要做：补货算法、图谱、指标计算。

按四样交付：变更文件清单、启动命令、验证脚本、最可能出问题的地方。
验证脚本必须覆盖：六类角色各发一次越权请求，断言全部被拒。
```

### 3.2 阶段二：知识与数据

```
做阶段二：知识与数据层。前置条件：阶段一已跑通。

范围：
- 建表（主数据、业务事实、规则台账、证据台账、指标口径、就绪度、图谱、审计）
- CSV 导入（含商品编码映射，未命中映射的数据必须进隔离表，不进主流程）
- 规则与证据台账的初始化数据（用 f00–f55 这套编号体系）
- 图谱构建（六类节点、七类关系，关系类型见方案报告 4.3）
- 溯源接口 /api/v1/trace/{object_id}，返回三跳的规则链与责任人

关键要求：
- 图谱构建不能依赖大模型抽取，必须从结构化字段自动生成，可重复执行且结果稳定
- 三跳查询用递归 CTE，不要用多次查询在 Python 里拼
- 指标口径表里 signed_at 为空的指标，查询时返回阻塞状态，不许返回 0 或估算值

按四样交付。验证脚本必须覆盖：任取一条建议能返回三跳链；编码未映射的数据被隔离。
```

### 3.3 阶段三：建议主链路

```
做阶段三：补货建议主链路。前置条件：阶段一二已跑通。

链路：就绪度评估 → 基线建议量 → 兜底判定 → 待签核单据 → 签核留痕。

关键要求：
- 兜底判定必须在服务端执行，不允许放在提示词里让模型判断
- 命中兜底时不返回建议量，只返回停止原因、规则编号、接手人、要求的人工确认时间
- 建议理由里出现的每个数字，必须能在结构化字段中找到来源，不允许模型自己算一个数写进解释
- 创建待签核单据与确认签核必须是两个独立动作，创建不构成授权
- 签核时校验签核人角色，且不能是提交人本人（运营总监终裁除外）

按四样交付。验证脚本必须覆盖：五类兜底情形逐个构造，断言全部被拦截。
```

## 4. 校验与评审提示词

```
不要改代码。先按下面五条审一遍你刚才的产出，逐条给结论（通过 / 不通过 + 位置）：

1. 红线检查：R1–R10 每一条，在代码里的落点在哪一行？有没有哪一条只写在注释里、实际没生效？
2. 越权检查：六类角色的权限矩阵，有没有任何一条路径能绕过？特别是系统服务账号。
3. 兜底检查：五类情形能否全部触发？有没有可以构造出来的绕过路径（比如同时传两个条件让判定短路）？
4. 审计检查：一笔单据从创建到签核，审计表能不能完整重建？缺哪个字段？
5. 数据检查：如果数据库是空的，接口返回的是明确的"未就绪"，还是一个看起来正常的 0？

第 5 条最容易出错，重点看。
```
